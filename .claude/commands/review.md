# /review — コードレビュースキル

このスキルは CODING_RULES.md に基づくコードレビューを自動実行し、
REVIEW.md に累積版として結果を追記する。

## 実行手順

### Step 1: レビュー対象の確認

引数（`$ARGUMENTS`）が指定されていればそのファイルを対象とする。
指定がなければ `git diff main...HEAD --name-only` で変更ファイルを特定する。

### Step 2: 規約の読み込み

CODING_RULES.md を読み込み、レビューの判断基準とする。

### Step 3: コードレビューの実行

以下の観点で各ファイルを分析する。

**設計観点**
- モジュールパターン（IIFE / 関数宣言）が CODING_RULES §2.1 に従っているか
- 責任分離が明確か（単一責任原則）
- 依存の方向が単方向で循環がないか

**コーディング規約観点（CODING_RULES §4 の必須事項）**
- forEach を使用していないか（→ for...of に置き換え）
- var を使用していないか（→ const / let に置き換え）
- 単行 if/for に波括弧がないものがないか
- switch に default: がないものがないか
- Yoda 条件（null === x 等）がないか

**コーディング規約観点（CODING_RULES §4 の推奨事項）**
- `||` の代わりに `??` が使えるケースがないか
- アロー関数の引数1つで `()` が省略できるケースがないか
- オプショナルチェーン `?.` が使えるケースがないか

**堅牢性観点**
- エラーハンドリングが CODING_RULES §5 に従っているか
- null / undefined の安全処理が漏れていないか
- JSDoc の @param, @returns, @throws が揃っているか

**テスト観点**
- テストコードが存在するか
- エッジケース（null, 空配列, 境界値）がカバーされているか

### Step 4: 指摘事項の重要度分類

発見した問題を以下に分類する。

| ランク | 分類基準 |
|---|---|
| H（High） | バグ、データ損失・漏洩リスク、セキュリティ脆弱性 |
| M（Medium） | 堅牢性・保守性への影響。方針決定が必要 |
| L（Low） | スタイル・改善提案。影響は軽微 |

### Step 5: REVIEW.md への追記

REVIEW.md が存在しなければ作成する。
存在すれば「レビュー版一覧」テーブルに1行追加し、新しい版のセクションを末尾に追記する。

追記フォーマット:

```markdown
---

<a name="第N版"></a>

# 第N版 — {対象ファイル・PRの概要}（{レビュー日: YYYY-MM-DD}）

- **対象**: {ファイル名一覧}
- **レビュー範囲**: 設計・コード・コーディング規約適合性

## 指摘事項

### {ID} [{重要度}]: {概要} {[修正済み] または空欄}

**ファイル**: `{ファイル名}:{行番号}`

{問題の説明}

```{言語}
// 修正前
{コード}
// 修正後
{コード}
```

## 修正サマリー

| ID | 重要度 | ファイル | 概要 | ステータス |
|---|---|---|---|---|
| {ID} | {H/M/L} | {ファイル} | {概要} | 未対応 / **修正済み** |

**要対応 N件。**
```

### Step 6: 結果の表示

レビュー完了後、以下を表示する。

```
レビュー完了:
  新規指摘: H×N, M×N, L×N
  要対応: N件
  REVIEW.md 第N版 を作成しました
  
次のアクション:
  - 修正が必要な場合: 問題を修正して再度 /review を実行
  - 修正が不要な場合: /pr を実行して PR を作成
```

## 使い方

```
/review                          # git diff main...HEAD の変更ファイルをレビュー
/review SlackFilters.gs          # 特定ファイルをレビュー
/review SlackFilters.gs SlackResolvers.gs  # 複数ファイルをレビュー
```
