# インボイス番号（適格請求書発行事業者公表システム）Web-API 調査メモ

## APIの概要

国税庁が提供する、適格請求書発行事業者（インボイス登録事業者）の公表情報を照会するREST API。

- **提供元**: 国税庁 課税部軽減税率・インボイス制度対応室
- **公式サイト**: https://www.invoice-kohyo.nta.go.jp/web-api/index.html
- **アーキテクチャ**: REST（GET）
- **レスポンス形式**: CSV / XML / JSON（`type` パラメータで切り替え）

## ベースURL・エンドポイント

| 環境 | ベースURL |
|------|-----------|
| 本番 | `https://web-api.invoice-kohyo.nta.go.jp` |
| 検証 | （公式サイト参照。アプリケーションIDは本番・検証共通） |

### エンドポイント一覧

| パス | 機能 |
|------|------|
| `GET /1/num` | 登録番号による事業者情報照会（最大10件/リクエスト） |
| `GET /1/diff` | 指定期間内の差分（更新）情報取得 |

バージョンプレフィクスは `/v1/` ではなく `/1/` であることに注意。

## 認証

- **方式**: クエリパラメータ `id` にアプリケーションIDを付与（ヘッダ認証ではない）
- **取得方法**: 国税庁への届出申請が必要（メールアドレス登録→申請フォーム→メール受領）
- 申請ページ: https://www.invoice-kohyo.nta.go.jp/web-api/pre-reg

## リクエストパラメータ（GET /1/num）

| パラメータ | 必須 | 型 | 説明 |
|---|---|---|---|
| `id` | ○ | string | アプリケーションID |
| `number` | ○ | string | 登録番号。`T` + 13桁数字。カンマ区切りで最大10件 |
| `type` | ○ | string | レスポンス形式。`01`=CSV, `11`=XML, `21`=JSON |
| `history` | ○ | string | `0`=最新のみ, `1`=全履歴 |

リクエスト例:
```
GET https://web-api.invoice-kohyo.nta.go.jp/1/num?id=APPID&number=T1234567890123&type=21&history=0
```

### フィールド意味一覧

| フィールド | 意味 |
|---|---|
| `lastUpdateDate` | 公表データの最終更新日 |
| `count` | 取得件数 |
| `divideNumber` | 分割番号（大量データ時） |
| `divideSize` | 分割サイズ |
| `announcement[].sequenceNumber` | 一連番号 |
| `announcement[].registratedNumber` | 登録番号（T+13桁） |
| `announcement[].process` | 処理区分 |
| `announcement[].correct` | 更正区分 |
| `announcement[].kind` | 人格区分（法人/個人等） |
| `announcement[].country` | 国内/国外区分 |
| `announcement[].latest` | 最新履歴フラグ |
| `announcement[].registrationDate` | 登録年月日 |
| `announcement[].updateDate` | 更新年月日 |
| `announcement[].disposalDate` | 取消年月日 |
| `announcement[].expireDate` | 失効年月日 |
| `announcement[].address` | 所在地 |
| `announcement[].addressPrefectureCode` | 都道府県コード |
| `announcement[].addressCityCode` | 市区町村コード |
| `announcement[].kana` | カナ表記 |
| `announcement[].name` | 氏名または名称 |
| `announcement[].tradeName` | 屋号 |
| `announcement[].popularName_previousName` | 通称・旧名 |

## 検証環境

- アプリケーションIDは本番・検証で共通使用可
- テスト用登録番号: `T0000000000016`、`T0000000000017` 等（架空データ）

## 既存クライアントとの比較・実装設計メモ

### GBizInfoApiClient との主な違い

| 観点 | GBizInfoApiClient | InvoiceApiClient (未実装) |
|---|---|---|
| 認証方式 | カスタムヘッダ (`X-hojinInfo-api-token`) | クエリパラメータ `id` |
| バージョンプレフィクス | `/v1/`, `/v2/` | `/1/` （数字のみ、変更の可能性低） |
| レスポンス形式切り替え | なし（常にJSON） | `type` パラメータ（常に `21` を使う想定） |

### 認証の扱い方

アプリIDをクエリパラメータとして全リクエストに付与する必要がある。
既存の `withBearerAuth` はヘッダ注入なので流用不可。

選択肢A: **transport decorator** として `withQueryAuth` を実装し、全URLに `id=...` を付与する。
選択肢B: `createClient` の `baseUrl` に `?id=xxx` を含めてしまう（簡易だが URL 結合の安全性要確認）。

→ 選択肢Aが設計上クリーン（GBizINFO の headerデコレータと対称的）。

### バージョン管理

現状 `/1/` のみ。Rule of Three に従い、バージョンオプションは不要（将来 `/2/` 登場時に対応）。

### responseHandler

常に `type=21`（JSON）を想定し、`response.body` をそのまま返す（GBizINFO と同じ）。

### 実装優先度

- GAS版・Node.js版ともに既存パターン（GBizInfoApiClient）を踏襲すれば実装コストは低い
- 認証デコレータ（クエリパラメータ版）のみが新規設計が必要な箇所
