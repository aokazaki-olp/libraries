# API認証のライブラリ設計に関する考察

## 背景

libraries/ に国税庁インボイス番号API (`InvoiceApiClient`) を追加するにあたり、認証情報（アプリケーションID）が **クエリパラメータ** で渡される点が、既存の `GBizInfoApiClient` (ヘッダ認証) や `withBearerAuth` (Bearer) と異なるため、認証をライブラリでどう表現するかを再考した。

## 既存パターンの構造的弱点

`GBizInfoApiClient` は `withBearerAuth` 相当の **デコレータ最外層** に認証を配置し、`withLogger` が headers を観測しない前提でトークン流出を回避している。

```
createClient → withRetry → withLogger
              ↑ ここに認証ヘッダが既に乗っている
```

これは **コンベンションによるセキュリティ**であり、構造的保証ではない。`.extend()` の順序が入れ替わった瞬間に流出する。コメントで「Logger は headers を観測しない前提」と注意書きしているのが暗黙ルールに頼っている証拠。

## 検討した3案

### 案① デコレータ + 順序注意 (現状踏襲)
- gBizInfo と同じく `withQueryAuth` を最外層に置く
- Pro: 既存と一貫
- Con: 順序依存。ロガーが URL を観測する設計だと毎回危ない

### 案② Transport の組み立て設定に格上げ
- `HttpCore.createTransport({ credentials: { query, headers } })`
- 認証情報は最内層の fetch 直前で適用、Request オブジェクトには載らない
- Pro: 構造的に観測不可能。順序入れ替えで壊れない
- Con: HttpCore の API 変更、既存クライアントの移行が必要

### 案③ `createClient` に `auth` フィールドを持たせる
- `ApiClient.createClient({ ..., auth: { query: {...} } })`
- `.extend()` とは独立した特権スロットとして扱う
- Pro: HttpCore 変更不要。「認証は extend より特別」を API で明示
- Pro: Bearer/Query/Basic を統一的に扱える拡張余地

## AuthProvider 抽象化について

AWS SDK / Octokit / google-auth-library が採用する `AuthProvider` interface パターンも検討したが、現状のコードベース (gBizInfo/Salesforce/Invoice の3つ) で interface 化のメリットが出るケースは存在しない。

- gBizInfo: 静的ヘッダ
- Invoice: 静的クエリ
- Salesforce: 動的だが `SalesforceAuth.ts` で既に独立解決済み

AuthProvider が活きるのは「動的認証 (OAuth refresh / SigV4 署名) を統一インターフェースで扱いたい」「同一クライアントで認証手段を差し替えたい」ケース。今のところ該当しない。

CLAUDE.md の「Don't design for hypothetical future requirements」「premature abstraction を避ける」原則からも、現時点では入れない判断が妥当。

## 結論（保留中の今後の方向）

理想は **案③（`auth` を設定スロット化）**。

ただし `withBearerAuth` を deprecated にする波及があるため、当面は **案①（`withQueryAuth` 追加）でシンプルに実装**する。利用者が自分一人なのでログにIDが乗っても許容できる。

将来、以下のいずれかが起きたら案②/③へリファクタする:
- ライブラリを他人に渡す
- 動的認証 (OAuth refresh) を統一したくなる
- 認証種別が4つ以上に増える
